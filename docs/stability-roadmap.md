# Короткий roadmap стабилизации tbssa

Этот файл фиксирует не новые большие функции, а наиболее полезные улучшения после завершения основного этапа разработки.

Цель: довести проект до состояния, где им удобно и безопасно пользоваться в повседневной эксплуатации, а диагностика проблем занимает минимум времени.

## 1. Разделить SSH и ICMP в модели состояния

Сейчас проект уже перешёл на `SSH-first` логику, но в данных и UI всё ещё можно усилить прозрачность.

Что стоит сделать:

- хранить отдельно `last_ssh_ok` и `last_icmp_ok`;
- хранить отдельно время последних успешных/неуспешных проверок;
- явно показывать в карточке сервера:
  - подтверждённый SSH-статус,
  - вспомогательный ICMP-статус.

Ожидаемая польза:

- исчезает путаница вида “сервер зелёный, но reboot не работает”;
- причина проблем читается прямо из UI без ручного расследования по логам.

## 2. Улучшить диагностику ошибок SSH

Что стоит сделать:

- различать типы SSH-провалов:
  - `port 22 closed`,
  - `timeout`,
  - `auth failed`,
  - `host key mismatch`,
  - `known_hosts problem`;
- сохранять последнюю причину провала в БД или в оперативном кеше;
- показывать её в карточке сервера или в отдельной кнопке диагностики.

Ожидаемая польза:

- администратор видит не просто “SSH недоступен”, а понимает, что именно сломалось.

## 3. Добавить отдельную серверную диагностику

Что стоит сделать:

- оставить кнопку `Проверить SSH` как быструю live-проверку;
- при необходимости добавить кнопку `Диагностика`, которая показывает:
  - live SSH,
  - live ICMP,
  - подтверждённый статус мониторинга,
  - последнюю известную ошибку.

Ожидаемая польза:

- ручная проверка становится понятной и пригодной для эксплуатации без чтения системных логов.

## 4. Усилить наблюдаемость мониторинга

Что стоит сделать:

- добавить более явные audit-события мониторинга;
- унифицировать тексты уведомлений `SSH up` / `SSH down`;
- по возможности сократить “шумные” повторяющиеся логи и оставить только полезные переходы состояний.

Ожидаемая польза:

- проще расследовать проблемы по журналу;
- меньше лишнего шума в production-логах.

## 5. Подготовить recovery-процедуры для Windows SSH

Что стоит сделать:

- добавить в документацию короткий recovery-раздел для случая падения `sshd`;
- выделить отдельный “аварийный минимум” команд:
  - проверить `sshd_config`,
  - проверить host keys,
  - проверить ACL,
  - проверить OpenSSH Operational log.

Ожидаемая польза:

- сбой SSH на Windows восстанавливается быстрее и без долгого повторного расследования.

## 6. Подготовить backup и восстановление проекта

Что стоит сделать:

- описать backup:
  - `data/tbssa.db`,
  - `.env`,
  - `known_hosts`,
  - SSH-ключей, если это допустимо вашей политикой;
- описать пошаговое восстановление на новом хосте.

Ожидаемая польза:

- проект проще переносить и безопаснее сопровождать.

## 7. Продолжить production-эволюцию MAX

MAX уже переведён с long polling на webhook и работает через публичный HTTPS endpoint. Следующие улучшения относятся не к UI, а к эксплуатационной устойчивости этого канала.

Что стоит сделать:

- продумать health-check и restart strategy;
- добавить регулярную проверку доступности webhook endpoint;
- проверить поведение после сетевых сбоев и временной недоступности MAX API.

Ожидаемая польза:

- MAX становится более зрелым production-каналом, а не просто дублирующим интерфейсом.

## Приоритет

Если делать только самое важное, разумный порядок такой:

1. разделение SSH/ICMP статусов;
2. улучшение SSH-диагностики;
3. recovery-процедуры для Windows SSH;
4. backup / restore;
5. дальнейшая production-эволюция MAX.

## Статус

На текущий момент это именно backlog улучшений после основного этапа реализации. Перед выполнением каждого пункта желательно опираться на результаты живого ручного тестирования из `manual-test-checklist.md`.
